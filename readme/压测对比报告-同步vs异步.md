# EduRAG 集成问答系统 · 同步版 vs 异步版 压测对比报告

- 测试时间：2026-10-24 11:47 – 12:15（两轮连续执行，宿主条件相同）
- 被测对象：`app.py`（Flask 开发服务器，5000）/ `app_async.py`（FastAPI + uvicorn 单进程，8000）
- **结果**：本次测试后已按结论定稿——只保留异步版，`app.py` 于 2026-10-24 从代码库移除；本报告作为选型依据留档
- 运行环境：conda `edurag`（Python 3.12）、RTX 4060 Laptop、MySQL / Redis / Milvus 全部本地
- 压测脚本：当时用 `loadtest/bench_qa.py`（单场景）+ `loadtest/run_suite.py`（成套调度）+ `loadtest/compare_suite.py`（汇总对比表），
  2026-10-24 清理仓库时已移除，现仅保留原始明细，复测需先恢复脚本或改用其它工具
- 原始明细：`loadtest/results/*_sync_*.json` 与 `*_async_*.json`
- 汇总：`loadtest/results/suite_sync.json`、`suite_async.json`

## 一、结论摘要

| 结论 | 数据支撑 |
|---|---|
| **FAQ 链路上异步版有数量级优势** | 并发 8：P95 从 **1546 ms → 37.3 ms（−97.6%）**，吞吐 **6.51 → 170.1 req/s（×26）** |
| **同步版的瓶颈不在检索算法** | 相同输入，服务端自报检索耗时 P50 仅 4.0 ms；RTT 却有 182.7 ms，**98% 的延迟在框架与会话落库** |
| **主因是「每请求新建线程 → 每请求新建 MySQL 连接」** | 实测 MySQL 建连 **168 ms**；`app.py` 用 Flask 开发服务器（一请求一线程），`chat_store` 的线程本地连接因此永远复用不上 |
| **RAG 链路上异步版暂无优势，并发 4 时反而更差** | 并发 2 基本持平（P50 33.2 s vs 29.8 s）；并发 4 时 **59.1 s vs 38.7 s（+52.7%）**，因 `RAG_CONCURRENCY=2` 排队 |
| **两版行为完全一致** | 7 个场景引擎分布逐一相同（295 faq + 5 none、RAG 100% 命中），失败数均为 0 |

## 二、口径同步（本次对比的前提）

要把两版放在同一把尺子上，以下四项必须逐项对齐，报告中所有数字均满足：

| 对齐项 | 做法 |
|---|---|
| **场景与参数** | 完全沿用 10-23 基线的 7 个场景（FAQ c1/c4/c8/c16、FAQ 热缓存 c8、RAG c2、RAG c4），请求数与并发数一字不改 |
| **缓存状态** | 每个 FAQ 场景开跑前清空 Redis `answer:*`（本轮每轮删除 295–776 条），保证「全冷 BM25」起始状态一致 |
| **指标颗粒度** | 与基线报告同一套：端到端 RTT 的 mean/P50/P90/P95/P99/max，外加服务端自报 `elapsed`（只含 `answer_query` / `_route` 内部计时）与吞吐、命中率 |
| **宿主条件** | 同一台机器、同一时间窗内先后执行；两个服务均把 stdout 重定向到文件、共用同一份 `logs/app.log`；每轮开测前确认端口释放与模型预热完成 |

> 之所以**不**直接拿本次异步数据去比 10-23 的同步基线：本次实测 MySQL 建连已从当时的毫秒级恶化到 **168 ms**，
> 这个变量会把结论完全带偏。因此另行在同场次重跑了一遍同步版，用「今天 vs 今天」的 A/B 作为主结论，
> 10-23 基线仅作参照（见第六节）。

## 三、环境与配置差异

| 项目 | 同步版 `app.py` | 异步版 `app_async.py` |
|---|---|---|
| Web 服务器 | Flask 开发服务器（werkzeug，`threaded`，**一请求一线程**） | uvicorn 单进程，事件循环 + anyio 线程池 |
| 并发控制 | 无闸门 | FAQ 16 / RAG 2 / DB 32（`CapacityLimiter`），线程池总容量 58 |
| MySQL 连接 | `chat_store` 线程本地连接，线程不复用 → **每请求新建连接** | 线程池固定线程 → **连接复用** |

| 幂等合并 | 无 | 相同 (问题, 模式, 学科, 会话) 并发合并（single-flight） |
| 空载 `/health` 基线（c=1，n=20） | 11.5 ms | **1.9 ms** |

### 4.4 并发扩展性（吞吐 / P95）

| 并发 | 同步吞吐 | 同步 P95 | 异步吞吐 | 异步 P95 |
|---|---|---|---|---|
| 1 | 5.36 | 219.5 ms | 72.08 | 15.0 ms |

## 五、RAG 链路对比

| 场景 | 并发 | 版本 | 总耗时 | 吞吐 | Mean | P50 | P90 | P95 | P99 | Max |
|---|---|---|---|---|---|---|---|---|---|---|
| RAG | 2 | 同步 | 395.2 s | 0.06 | 31.95 | 29.76 | 43.24 | 44.37 | 50.16 | 51.88 |
| RAG | 2 | 异步 | 397.5 s | 0.06 | 32.04 | 33.21 | 40.96 | 41.04 | 42.21 | 42.56 |
| RAG | 4 | 同步 | 120.5 s | 0.10 | 36.93 | 38.70 | 44.14 | 45.93 | 47.51 | 47.91 |
| RAG | 4 | 异步 | 194.0 s | 0.06 | 56.95 | 59.09 | 73.97 | 74.52 | 74.73 | 74.78 |

- **并发 2：基本持平**（P50 33.2 s vs 29.8 s，属上游大模型正常波动区间），框架开销两版都可忽略
  （同步 0.19 s / 异步 0.009 s，占 30 秒的比例 < 1%）。
- **并发 4：异步版慢 52.7%**。原因是 `RAG_CONCURRENCY=2` 把 4 个并发请求压成 2 个并行 + 2 个排队，
  单个请求 RTT 里包含了排队时间；同步版没有闸门，4 路同时打上游，总耗时反而更短（120 s vs 194 s）。
- 结论：**RAG 的瓶颈 100% 在上游大模型**，与 Web 框架无关。异步版在该链路的收益只在「不被打爆」，
  当前默认的 `RAG_CONCURRENCY=2` 对远端 API 而言过于保守。

## 六、归因：97% 的差距从哪来

以并发 1 为例（无竞争，最适合拆解）：

```
同步 RTT P50 182.7 ms
  ├─ 检索处理（服务端自报）        4.0 ms
  ├─ HTTP 框架开销（/health 基线） 11.5 ms
  └─ 会话落库（MySQL 建连 168 ms） ← 占 92%
异步 RTT P50 13.0 ms
  ├─ 检索处理                      4.4 ms
  ├─ HTTP 框架开销（/health 基线）  1.9 ms
  └─ 会话落库（连接复用）          ≈6.7 ms
```

三个独立因子的贡献：

1. **每请求新建 MySQL 连接（主导，~168 ms）**：`chat_store` 用线程本地连接做复用，
   但 Flask 开发服务器是「一请求一线程」，线程用完即弃，连接随之失效。
   FastAPI 侧走 `run_sync` 固定线程池，连接稳定复用 —— 这是本次差距的最大来源，且**与「同步/异步」本身无关**，
   属于连接管理策略的差异。
2. **开发服务器 vs ASGI 服务器（~10 ms）**：空载 `/health`，同步 11.5 ms，异步 1.9 ms。
3. **并发下的放大效应（并发 ≥4 才出现）**：同步版从 c4 起，服务端自报耗时也开始膨胀（4 ms → 174 ms），
   说明线程数暴涨后 GIL 争抢与连接风暴已经把检索本身拖慢；异步版用固定线程池把这一项压住了。

> **必须说明的局限**：如果把 MySQL 建连恢复到正常水平（<5 ms，10-23 基线时的状态），
> 同步版 c1 的 RTT 会回落到 20 ms 量级，与异步版的差距将缩小到 30–50%；
> 但并发 8 时同步版依然会因「一请求一线程 + 开发服务器」而明显劣化。
> 因此**「异步快 26 倍」这一结论的成立前提是当前这台机器的 MySQL 建连异常**，不能直接推广到所有部署环境。
> 真正稳健的结论是：异步版消除了「并发上升 → 延迟线性劣化」这一结构性缺陷。

## 八、建议（按实测收益排序）

1. **只保留 `app_async.py`（已执行）**：FAQ P95 从 1.5 s 级降到 37 ms 级，接口与返回结构不变，
   前端零改动。同步入口与 `qa_router.answer_query` 一并删除，避免两套编排逻辑漂移。
2. **若未来还要回到 WSGI 形态**：必须换 `waitress` 等生产级服务器，并给 `chat_store` 换连接池
   —— 绝不能再用「一请求一线程」的开发服务器。仅这一项即可把 FAQ P95 从 1546 ms 拉回 100 ms 量级。
3. **排查 MySQL 建连 168 ms 的异常**：正常应 <5 ms。优先检查 `skip_name_resolve` 是否关闭（反向 DNS 解析）
   与连接握手阶段的认证插件耗时。这是当前所有版本的共同隐性成本。
4. **重新评估 `RAG_CONCURRENCY`**：远端大模型是 I/O 等待，限 2 会让并发 4 的吞吐腰斩
   （0.10 → 0.06 req/s）。建议按上游配额放宽到 4–8，或改为「按供应商 QPS 配额限流」。
5. **`FAQ_CONCURRENCY` 收敛到 4–8**：16 核下 c8 是吞吐峰值（170 req/s / P95 37 ms），
   给到 16 反而降到 123.6 req/s 且 P95 涨到 668.7 ms。

## 九、局限与说明

- 两版均为**单进程**部署，未测多 worker（`workers>1` 会让进程内共享的 BM25 索引与 BGE 模型重复加载，需另测显存占用）。
- 压测请求真实写入 `conversations` 表，会话记录留在库中；Redis `answer:*` 每轮开测前被清空（缓存可再生，不影响业务数据）。
- RAG 依赖公网大模型服务，不同时段有 10–30% 波动；本轮 RAG 两版各 24 + 12 个样本，P99 参考价值弱于 P95。
- RAG 场景未触发检索分支（意图分类仍判为「通用知识」），测的是 LLM 直答路径，**不含 Milvus 检索与 BGE 精排**；
  该问题与 10-23 基线相同，待意图分类模型修复后需重测。
- 同步版使用 Flask 开发服务器（`app.run`），异步版使用 uvicorn 单进程，这是两版代码里既定的启动方式，
  未做「Flask + waitress」的额外组合测试。
