## 四、关键发现

**1. 本次 RAG 未触发检索分支。**
全部请求都命中 `查询为通用知识,不检索知识库,直接由大模型作答`。单独验证意图分类器，对「Java 多线程」「二叉树遍历」「数据库索引」等专业问题也一律输出 `通用知识 [0.995, 0.005]`，模型塌缩到单一类别。
因此上述 RAG 数字是「LLM 直答」路径的延迟，**不含 Milvus 检索与 BGE 精排**。按你的要求，模型训练问题本次不处理。

**2. FAQ 的瓶颈不在检索。**
服务端检索 4.6 ms，端到端 84 ms；`/health` 基线 12 ms，`chat_store.add_exchange` 落库仅 0.1 ms。剩余约 70 ms 来自单进程 Flask 处理与每请求 3–4 条 INFO 日志同步写盘的锁竞争。并发从 1 到 16，检索耗时几乎不变（1.7 → 4.6 ms），RTT 却涨 4.9 倍。

## 五、优化建议（按收益排序）

1. **换生产级服务器**：Windows 用 `waitress`，或 Linux 用 `gunicorn`/`uvicorn` 多 worker。这是 FAQ P95 从 117 ms 回落到 20 ms 量级的关键，收益最大。
2. **日志降级或异步化**：每请求 3–4 条 INFO 同步落盘，是并发下延迟线性增长的直接原因。
3. **RAG 流式输出（SSE）**：首字延迟可降至 1–2 s，把 30 s 的等待变成可接受体验；同时给 LLM 调用加超时与重试上限。
4. **RAG 结果缓存**：重复问题直接省掉 30 s，当前性价比最高。

## 六、测试方法与局限

- 固定并发数 + 队列派发，每个 worker 独立 `requests.Session`。
- FAQ 输入取自 `knowledge` 表 467 条真实问题，每问题只请求一次以避开 Redis 缓存；冷路径通过问号变体强制走 BM25。
- 分位数用 `numpy.percentile` 线性插值。RAG 的 P99 在 n=44 时接近最大值，参考价值弱于 P95；要稳定 P99 需 ≥100 样本（约 50 分钟）。
- 被测服务是单实例开发服务器，**数据不代表生产部署能力**；压测请求已真实写入 `chat_store`，对话记录留在库中。
- RAG 依赖公网 DashScope，延迟受网络与上游负载影响，不同时段会有 10–30% 波动。
- 原始明细见 `loadtest/results/*.json`。
