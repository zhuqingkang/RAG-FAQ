# EduRAG · 容量与部署建议手册

> 本手册用**本机实测数据**推算不同并发规模所需的算力资源。
> 所有推算都标注了公式与假设，便于你按实际并发重算；文末给出可直接复测的步骤。
>

## 0. 先明确口径（否则数字会差 20 倍）

讨论「并发」前必须先区分两件事，本项目两者差一个数量级：

| 口径 | 含义 | 典型值 | 换算关系 |
|---|---|---|---|
| **并发请求数 C** | 同一时刻在途的 HTTP 请求数 | 压测用的就是它 | — |
| **QPS** | 每秒完成的请求数 | 生产监控看它 | `QPS = C / 平均响应时间 T` |
| **在线用户数 U** | 打开页面的用户数 | 业务方常说它 | `U ≈ QPS × 用户提问间隔`（问答场景 30~60 s） |

换算示例：100 个**在线用户**，每人 30 s 问一句 → 约 3.3 QPS → 在 RAG 30 s 响应下只对应 **100 个并发请求**吗？不是，`C = QPS × T = 3.3 × 30 = 100`。巧合相同，但若响应降到 3 s，并发只有 10。

**本手册统一按「并发请求数」写**。若你手上是"在线用户数"，先乘提问率换成 QPS 再乘响应时间。

## 1. 本机基线：硬件与已设参数

### 1.1 硬件

| 项 | 实测值 | 说明 |
|---|---|---|
| CPU | 8 物理核 / 16 逻辑核 | Windows 11，`os.cpu_count() = 16` |
| 内存 | 31.2 GB | 常驻占用约 6~8 GB（Milvus/MySQL/Redis 本地） |
| GPU | RTX 4060 Laptop，**8 GB**，24 SM | 显存是本地部署的硬约束 |
| 显存占用 | BGE-M3 ≈ 2.2 GB + bge-reranker-large ≈ 1.3 GB | **常驻 3.5 GB**，留给生成模型仅 ~4.5 GB |
| 磁盘 | 模型 + 向量库 + 日志 | 冷启动加载模型约 40~60 s |

### 1.2 已设置的并发与超时参数

参数集中在 `app_async.py`，可用环境变量覆盖：

| 参数 | 当前值 | 取值依据 |
|---|---|---|
| `FAQ_CONCURRENCY` | `max(4, CPU)` = **16** | jieba + BM25 是 CPU 密集，超过核数只会互相抢 GIL |
| `RAG_CONCURRENCY` | **2** | BGE-M3 + reranker + 生成模型同时占显存，再高单请求延迟成倍上升 |
| `DB_CONCURRENCY` | **32** | MySQL 小事务，线程本地连接 |
| 线程池总容量 | 16 + 2 + 32 + 8 = **58** | 与三个闸门对齐，避免假排队 |
| `FAQ_TIMEOUT` | 30 s | 正常 0.1 s，留足抖动余量 |
| `RAG_TIMEOUT` | 180 s | 需大于 `LLM_TIMEOUT`（60 s） |
| `[llm] timeout` | 60 s | 单次生成上限 |
| `[retrieval]` | k=3 / m=2 / 父块 1200 / 子块 300 | 精排后喂 2 个父块给 LLM |

### 1.3 实测性能（关键基线）

| 场景 | 并发 | 吞吐 | P95 | P99 |
|---|---|---|---|---|
| FAQ 冷缓存（端到端） | 8 | 170 req/s | 37.3 ms | 635.5 ms |
| FAQ 冷缓存（服务端 `elapsed`） | 8 | — | **17.8 ms** | 305.9 ms |
| FAQ 热缓存（端到端） | 8 | 360 req/s | 30.0 ms | 34.3 ms |
| FAQ 并发峰值 | 8 | **170 req/s** | 37.3 ms | 635.5 ms |
| FAQ 并发超配 | 16 | 123.6 req/s | 668.7 ms | 877.4 ms |
| RAG（云端 LLM） | 2 | **0.06 req/s** | 41.0 s | 42.2 s |
| RAG（单请求实测，历史） | 1 | — | 35~56 s / 536~1476 字 | — |
| 空载 `/health`（c=1, n=20） | 1 | — | 1.9 ms（均值） | 7.0 ms（最大） |

三个必须记住的结论：

1. **FAQ 的检索只占一小部分**：服务端自报 P50 12.8 ms，端到端 P50 31 ms，其余是 HTTP 框架与会话落库（连接已复用，不再每请求建连）。
2. **并发超过物理核数没有收益**：8 并发是吞吐峰值 170 req/s，给到 16 反而回落到 123.6 req/s，P95 从 37 ms 涨到 669 ms —— 闸门默认值 `max(4, CPU)` 在 16 核机器上偏大，实际取 4~8 更优。
3. **RAG 的瓶颈完全在上游大模型**。RTT 与服务端自报耗时差 < 30 ms，检索、落库均可忽略。

### 1.4 单请求的算力画像（推算的输入）

| 项 | 直答路径（本次实测） | 完整检索路径（含 Milvus + 精排） |
|---|---|---|
| 输入 token | ~50 | ~4000（2 个父块 ×1200 字 + 历史 1500 字） |
| 输出 token | **1600**（1006 字 × 1.6） | 1600 |
| 上游耗时 | 35~56 s | 需再加检索 0.3~0.5 s |
| 单请求字符产出 | 536 / 1476 字（两次实测） | 同量级 |

> 输出长度是算力成本的决定因素：**1600 token 输出 ≈ 9.6 万亿次浮点运算**（3B 模型每 token 约 2×3e9 FLOPs）。把输出压到 600 token，算力直接降到 37%。

## 2. 100 并发需要多少资源（分链路推算）

### 2.1 推算方法

用 Little's Law：`并发 C = 吞吐 QPS × 响应时间 T`

反解出**必须达到的吞吐**，再乘单请求算力，得到总算力需求：

```
所需 QPS = C / T
所需输出 token/s = QPS × 单请求输出 token
```

### 2.2 FAQ 链路（纯 CPU，100 并发很容易）

**目标**：100 并发、P95 ≤ 300 ms（提问类交互可接受的上限）

- `T = 0.3 s` → 需要 `QPS = 100 / 0.3 ≈ 334 req/s`
- 单请求服务端 12.8 ms（P50）→ 纯计算需 `334 × 0.0128 ≈ 4.3 核`
- 实测 8 并发 170 req/s 是单进程峰值，16 并发回落到 123.6 req/s（GIL + 线程超配），因此**必须多进程**

| 部署方式 | 单实例能力 | 达到 334 QPS 需要 |
|---|---|---|
| 当前异步版（uvicorn 单进程，16 核实测） | 170 req/s | 2 个实例 + 负载均衡 |
| 历史 Flask 开发服务器（已移除） | 105.8 req/s | 4 个实例 + 负载均衡 |
| `waitress`（Windows，4 线程） | 约 150~200 req/s | 2 个实例 |
| `gunicorn`（Linux，4 worker） | 约 250~350 req/s | 1~2 个实例 |

**结论：100 并发 FAQ 只需 4~8 核 + 8 GB 内存**，前提是继续用异步版（或至少换掉开发服务器）、并把 INFO 日志降级或异步化。当前异步版并发 16 时 P95 已回落到 0.67 s，比同步版的 3 s 好一个量级。

### 2.3 RAG 链路（100 并发是真正的分水岭）

**目标**：100 并发、P95 ≤ 30 s（当前水平）

- 需要 `QPS = 100 / 30 = 3.33 req/s`
- 单请求输出 1600 token → **总输出吞吐需 3.33 × 1600 ≈ 5300 token/s**

#### 方案 A：继续用云端 API（推荐起步方案）

不需要买卡，只需要把 `RAG_CONCURRENCY` 从 2 提到 100，并确认上游配额：

| 项 | 估算 |
|---|---|
| 需要的并发连接数 | 100（`C = 3.33 × 30`） |
| 上游 QPS 配额 | ≥ 3.4 |
| 输出 token 费用 | 5300 token/s × 3600 ≈ **1900 万 token/小时** |
| 费用量级 | 按 ¥0.01/千 token 计 ≈ **¥190/小时**（实际单价以供应商报价为准） |
| 本机资源 | 仅需 FAQ 的 4~8 核；GPU 不参与生成 |

**风险**：100 个并发连接同时打同一网关，容易被限流。需要向供应商确认 QPS/TPM 配额，或用多个 Key 轮询。

#### 方案 B：本地 vLLM（数据不出内网，但 8 GB 卡做不到）

先把显存账算清楚，这决定了单机能跑多大模型：

| 显卡 | 显存 | 扣掉 BGE（3.5 GB） | 可用模型 | 单请求解码 | **batch 后总吞吐** |
|---|---|---|---|---|---|
| RTX 4060 Laptop（本机） | 8 GB | 4.5 GB | 3B-AWQ | 40~60 tok/s | **150~250 tok/s** |
| RTX 4090 / 3090 | 24 GB | 20 GB | 7B fp16 或 14B-AWQ | 60~90 tok/s | **600~1000 tok/s** |
| A100 / H20 | 80 GB | 76 GB | 14B fp16 / 32B-AWQ | 90~120 tok/s | **3000~5000 tok/s** |

要凑够 5300 token/s：

| 方案 | 需要的卡数 | 可行性 |
|---|---|---|
| 4060 8G（本机） | **21~35 张** | ❌ 不现实 |
| 4090 24G | **6~9 张** | ⚠️ 成本高，且要自己做负载均衡 |
| A100 80G | **1~2 张** | ✅ 可行，适合私有化部署 |

> 表中吞吐为**工程经验估算**（基于显存带宽与 batch 规模），不是实测值。落地前必须用 `vllm bench` 或同类工具在你的卡上校准，误差可能达 ±40%。

**如果坚持用本机 8 GB 卡**：把输出限制在 600 token、并发降到 20、接受 P95 ≈ 60 s，才勉强可用。100 并发在本机上没有现实解。

#### 方案 C：本地 + 云端混合（性价比最高）

FAQ 与身份直答在本地（微秒~毫秒级），只有 RAG 走云端或大卡：

| 流量占比 | 说明 |
|---|---|
| 通常 60~80% 的问题能被 FAQ 命中 | 这部分完全不消耗 GPU/LLM 配额 |
| 剩余 20~40% 才进 RAG | 100 并发下，实际 RAG 并发只有 **20~40** |

按 30 并发重算：`QPS = 30/30 = 1 req/s`，输出只需 **1600 token/s** → 一张 4090 或半张 A100 就够，云端费用降到 ¥57/小时。**这是最该先做的优化：提高 FAQ 命中率比加机器便宜得多。**

### 2.4 汇总：不同并发规模的资源配置

| 并发请求 | FAQ 资源 | RAG 方案 | 内存 | GPU | 月成本量级（估算） |
|---|---|---|---|---|---|
| **≤ 10**（内网演示） | 单进程 | 云端，`RAG_CONCURRENCY=2` | 8 GB | 8 GB 卡（只跑 BGE） | API 费 |
| **50**（小团队） | waitress 1~2 实例，4 核 | 云端，`RAG_CONCURRENCY=50` | 16 GB | 同上 | API 费 ×5 |
| **100**（部门级） | waitress 2 实例 / 8 核 | 云端 或 1×A100 80G | 32 GB | A100 或纯云端 | API 费 ×10 或一次性卡费 |
| **500**（全院） | 4~8 实例 + Nginx | 云端多 Key 或 2~4×A100 | 64 GB+ | 多卡 | 需专门预算评估 |

## 3. 参数随并发实时调整表

改一个数就能匹配当前规模，不用改代码（`app_async.py` 顶部读环境变量）：

| 并发规模 | `RAG_CONCURRENCY` | `FAQ_CONCURRENCY` | `DB_CONCURRENCY` | `RAG_TIMEOUT` | 备注 |
|---|---|---|---|---|---|
| ≤ 10 | 2 | 16（默认 = CPU） | 32 | 180 s | 当前配置 |
| 50 | 50 | 16 | 32 | 120 s | 云端配额需 ≥ 1.7 QPS |
| 100 | 100 | 16 | 64 | 90 s | 云端配额 ≥ 3.4 QPS |
| 500 | 200~500 | 32 | 128 | 60 s | 必须多实例 + 负载均衡 |

三条调参铁律：

1. **`RAG_CONCURRENCY` 不能超过上游配额**，否则只是把排队从本地挪到供应商侧，还会触发限流报错。
2. **`RAG_TIMEOUT` 必须 > `LLM_TIMEOUT`**，否则闸门先超时、LLM 调用还在跑，算力白白浪费。
3. **本地 vLLM 的 `RAG_CONCURRENCY` 上限由 KV cache 决定**，超出后 vLLM 内部排队，表现为 P99 陡增。

补充：线程池总容量是 `FAQ + RAG + DB + 8` 自动计算的，把 `RAG_CONCURRENCY` 调到 100 时总线程数约 156。每线程默认保留 8 MB 栈空间（虚拟地址，非物理占用），200 线程以内无压力，但超过 500 线程建议改用 `asyncio + aiohttp` 直接异步调用 LLM，而不是继续加线程。

## 4. 比加机器更便宜的四个优化（按收益排序）

| 优化 | 效果 | 成本 |
|---|---|---|
| **提高 FAQ 命中率** | RAG 流量降 60~80%，算力需求同比例下降 | 补知识库、调阈值 |
| **限制输出长度**（`max_tokens=600`） | 1600 → 600 token，算力降到 37% | 改一个参数 |
| **SSE 流式输出** | 首字延迟 1~2 s，30 s 等待变得可接受，感知并发能力翻倍 | 前端 + 后端改造 |
| **RAG 结果缓存** | 重复问题直接省 30 s，问答场景重复率通常 20~40% | Redis 一层 |

> 先做完这四项，再谈加 GPU。「限输出长度」这一项的性价比尤其高：它同时降低延迟、成本和显存占用。

## 5. 怎么复测并校准手册里的数字

改完配置后需要实测，把手册里的估算替换成真实值。**压测脚本（`bench_qa.py` / `run_suite.py` / `compare_suite.py`）已于 2026-10-24 随仓库清理移除**，仓库内只保留 `loadtest/results/*.json` 的历史明细。

复测有两条路：恢复那套脚本，或换用任一对准 `POST /query` 的压测工具——但线程模型要与历史保持一致（固定并发数 + 队列派发，每个 worker 独立 `requests.Session`，请求体 `{"query": ..., "mode": "faq"|"rag"}`），否则数字不可比。

场景按历史明细的同口径来：

| 场景 | 并发 | 请求数 | 关注字段 |
|---|---|---|---|
| FAQ 冷缓存（问题各不重复） | 8 | 300 | `rtt_all.p95` / `qps` |
| FAQ 热缓存（同一问题连续请求） | 8 | 200 | 同上 |
| RAG（强制 `mode=rag`） | 目标并发 | ≥ 100（P95 才稳定） | `rtt_all.p95` |

新结果建议沿用 `{场景}_{批次}_c{并发}_n{请求数}.json` 命名，字段与 `results/` 里的历史文件同构，可直接对照。

校准要点：

- **只看 P95 和 QPS**，均值会被少数快请求拉偏（当前 RAG 均值 30 s、P95 40 s）。
- 每次只改一个参数，记录前后 P95，否则无法归因。
- RAG 的 P99 需要 ≥ 100 样本才有意义（约 50 分钟），样本不足时只看 P95。

## 6. 本手册的局限

1. **RAG 实测走的是「通用知识直答」路径**，未触发 Milvus 检索与 BGE 精排（意图分类器塌缩所致）。完整检索路径的输入 token 会从 ~50 涨到 ~4000，prefill 成本增加，但 decode 仍是主要成本。
2. **上游 LLM 有 10~30% 的时段波动**，云端方案的吞吐与延迟随之浮动。
3. **GPU 吞吐为工程估算**，基于显存带宽与 batch 规模推导，误差 ±40%，落地前需实测。
4. **费用按当前单价量级估算**，实际以供应商报价为准。
5. 所有实测均来自**单机、单实例、Windows 开发服务器**，不代表生产集群能力。

## 附录：100 并发的推算过程（便于复核）

```
已知：单请求输出 ≈ 1600 token（1006 字 × 1.6）
目标：100 并发，P95 ≤ 30 s

QPS  = 100 / 30        = 3.33 req/s
输出 = 3.33 × 1600     = 5328 token/s
输入 = 3.33 × 50       = 167 token/s（prefill，成本约为 decode 的 1/10）

云端：并发连接 = 3.33 × 30 = 100 条，需上游配额 ≥ 3.4 QPS
本地：5328 token/s ÷ 单卡吞吐
      ÷ 200  (4060 8G)  = 27 张
      ÷ 800  (4090 24G) = 7 张
      ÷ 4000 (A100 80G) = 1.3 张 → 2 张

若 FAQ 命中 70%，RAG 实际并发 30：
      QPS  = 1.0
      输出 = 1600 token/s → 4090 × 2 或 A100 × 1
```
