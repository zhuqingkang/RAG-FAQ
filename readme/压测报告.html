四、关键发现

发现 1（影响 RAG 口径）：本次所有 RAG 请求都走了「通用知识直答」分支，Milvus 检索与 BGE 精排未参与。
日志显示 100% 的请求命中 查询为通用知识,不检索知识库,直接由大模型作答。经单独验证，意图分类器对 「Java 多线程」「二叉树遍历」「数据库索引」等专业问题也一律输出 通用知识 [0.9947, 0.0053]， 即模型塌缩到单一类别。因此本报告的 RAG P95/P99 是 「LLM 直答」路径的延迟，不包含向量检索与重排序的开销。 按你的要求，该模型的训练问题本次不做处理。
发现 2（FAQ 的主要瓶颈不在检索）：服务端检索仅 4.6 ms，而端到端 84 ms。 空载 /health 基线 12 ms、chat_store.add_exchange 落库仅 0.1 ms， 剩余约 70 ms 来自单进程 Flask 处理与每请求 3–4 条 INFO 日志的文件 IO 争抢。 并发从 1 升到 16，服务端检索耗时基本不变（1.7 → 4.6 ms），但 RTT 涨了 4.9 倍。

4.1 优化优先级（按收益排序）

  • 换成 WSGI/ASGI 生产服务器：waitress（Windows）或 gunicorn/uvicorn 多 worker，可让 FAQ P95 从 117 ms 回落到 20 ms 量级——当前 Flask 开发服务器是最大瓶颈。
  • 降低日志级别或改异步日志：压测期间每请求 3–4 条 INFO 同步写盘，是并发下延迟线性增长的直接原因之一。
  • RAG 侧做流式输出（SSE）：首字延迟可降到 1–2 s，把 30 s 的「不可用感」转化为可接受的产品体验；同时给 LLM 调用设超时与重试上限。
  • RAG 结果缓存：同一问题的重复率较高时可命中缓存，直接省掉 30 s；这是当前性价比最高的 RAG 优化。

五、测试方法与局限

  • 压测工具为自研脚本 loadtest/bench_qa.py，走真实 HTTP 接口 POST /query，线程模型为固定并发数 + 队列派发。
  • FAQ 输入取自 MySQL knowledge 表 467 条真实问题，每个问题只请求一次，尽量避开 Redis 缓存；改写问号版本用于强制冷路径。
  • RAG 输入为 12 条技术类问题循环，强制 mode=rag 绕过 FAQ。
  • 分位数算法：numpy.percentile 线性插值。RAG 的 P99 在 n=44 时实际接近最大值，参考价值弱于 P95；若要稳定 P99 需 ≥100 样本（约 50 分钟）。
  • 被测服务为单实例、单进程、开发服务器，数据不代表生产部署能力；所有请求均真实写入 chat_store，压测产生的对话记录已留在库中。
  • RAG 依赖公网 DashScope 接口，其延迟受网络与上游负载影响，不同时段结果会有 10–30% 波动。
