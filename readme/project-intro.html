两条知识链路

面向教育领域的问答系统：先用 FAQ 精确检索 命中人工维护的标准答案，未命中再自动转 RAG 语义检索 + 大模型生成。对外只暴露一套页面、一个接口。

系统概况

2 条问答链路（FAQ / RAG）
1统一接口 POST /query
3并发闸门（FAQ / RAG / DB）
5.4GB 本地模型（BGE + BERT）
默认路由：auto —— FAQ 优先，未命中或异常自动转 RAG
Capabilities

两条链路，各解决一类问题

固定问答不该每次都让大模型重新生成，开放型问题又无法靠字面匹配命中——因此把两种检索范式并列，用统一路由决定走哪条。

FAQ 链路 精确 · 毫秒级

  • jieba 分词 → BM25Okapi 打分 → softmax 归一化 → 最高分 > 0.85 判定命中
  • 命中后用最相似的历史问题去 MySQL jpkb 表取标准答案
  • 答案写回 Redis answer:{query}，同字符串下次直接返回
  • 索引常驻内存，daemon 线程每 30 分钟以 MySQL 为准同步一次
答案来源：人工维护 · 不经过大模型，天然无生成式幻觉

RAG 链路 语义 · 秒级

  • BERT 意图分流：通用知识不检索直接作答，专业咨询才进检索
  • LLM 选策略 → 分派到回溯 / 子查询 / HyDE / 直接检索（不匹配则退化为直接检索）
  • BGE-M3 编码 query，dense(0.7) + sparse(0.3) 混合检索，召回 k=3
  • 子块命中后按 parent_content 去重还原父块，bge-reranker 精排取 Top2
  • DashScope 生成答案，附带来源说明与“信息不足请联系人工”的兜底句
答案来源：检索 + 生成 · 支持按学科（source）过滤

同一套前端、同一个 POST /query 接口，只是命中的链路不同。下图为本地环境实测截图，气泡右下角的徽标与耗时均由后端返回。

≈ 10,000×2.6 ms 与 26.7 s 的差距
毫秒级FAQ 命中即返回，适合高频固定问题
秒级RAG 答案现场生成，随长度与策略波动

说明：26.701 s 为本次样本实测值，包含「选策略 → 检索 → 精排 → 生成」多段耗时，属于偏慢的一次；RAG 实际耗时随问题复杂度、命中的策略与生成长度波动较大，不宜当作平均值。0.0026 s 为 FAQ 命中后的接口耗时。

Mechanisms

五个关键实现

路由判定只写一份，两个入口共用；检索、生成、存储各自独立可降级。

01 统一路由 qa_router

answer_query(question, mode, source_filter) 是唯一判定入口。两个服务只负责协议转换、会话与落库，避免同步版与异步版行为漂移。

autoFAQ 命中即返回，未命中/异常转 RAG
faq / rag强制单链路，便于压测与效果对照
返回值answer / engine / found / elapsed / note

02 父子块 + 混合检索

子块负责“检索准”，父块负责“上下文全”。命中子块后按父块正文去重还原，再用 CrossEncoder 精排。

切块父 1200 / 子 300 / 重叠 50
融合WeightedRanker(0.7 dense, 0.3 sparse)
精排reranker 取 Top2，候选 < 2 时跳过

03 幻觉四道闸

按请求顺序逐层收窄：能精确回答的不生成，要生成时压缩上下文，答不出时明确拒答。

入口闸BM25 阈值 0.85，直返人工答案
上下文闸混合检索 k=3 → 父块去重 → Top2
提示闸要求基于上下文、说明来源、内置兜底句
出口闸空答案统一兜底，found=false

04 异步并发模型

事件循环只做编排，阻塞调用全部下沉线程池；三条链路各自限流，互不拖累。

闸门FAQ = max(4, CPU) · RAG = 2 · DB = 32
超时FAQ 30 s · RAG 180 s · 整体 +10 s
去重single-flight，同刻相同 key 只算一次
进程workers=1，模型与索引进程内共享

05 意图分流 + 四策略分派

先判断问题类型，再决定检索方式：通用知识直接作答，专业咨询由 LLM 选策略后分派到对应检索器。

分类器models/bert_query_classifier 微调权重
四策略回溯 / 子查询 / HyDE / 直接检索
容错策略名不匹配时退化为直接检索
阶段耗时量级已落地的处理
FAQ 缓存命中亚毫秒Redis answer:{query}
FAQ BM25 打分几毫秒索引常驻内存
BGE-M3 编码 query10 ~ 40 ms模型常驻 + 启动预热
Milvus 混合检索50 ~ 300 ms连接复用 + segment 常驻
bge-reranker 精排20 ~ 100 ms候选 < 2 时跳过
LLM 生成1 ~ 10 s同刻重复请求由 single-flight 合并
Optimization

已落地的优化

只列出代码中真实存在的优化，按类别分组。每项都能在源码里找到对应位置。

STARTUP

重库延迟加载

torch / pymilvus / milvus-model / sentence-transformers 全部移到函数内 import，只 import 模块几乎零开销。

已落地
STARTUP

启动预热 + 单例

FAQ 同步预热（jieba + BM25）；RAG 后台线程加载，并主动触发 BGE / reranker 权重进显存。

已落地
BUILD

离线三级缓存

catalog / documents / chunks 三层 JSON，配 mtime+size 校验、原子写与版本号，二次建库不再全量 OCR。

已落地
LATENCY

FAQ 响应缓存

命中 BM25 后写入 Redis answer:{query}，同字符串请求降到亚毫秒。

已落地
LATENCY

索引常驻 + 定时同步

BM25 索引常驻内存，30 分钟 daemon 线程以 MySQL 为准覆盖同步，知识库更新不必重启。

已落地
CONCURRENCY

三闸门 + 分层超时

CPU 密集型、GPU/模型、SQLite 各自限流；线程池容量与闸门对齐，避免假排队。

已落地
CONCURRENCY

single-flight 去重

同刻相同 (question, mode, source) 只算一次，其余请求共享同一个 Future。

已落地
RETRIEVAL

意图分流 + 四策略

分类器加载微调权重：通用知识直接作答；专业咨询由 LLM 选策略后分派到回溯 / 子查询 / HyDE / 直接检索。

已落地
QUALITY

父子块 + 精排

子块 300 检索、父块 1200 喂模型，父块去重后 reranker 取 Top2，压缩噪声。

已落地
ENGINEERING

判定收口 + 失败降级

路由逻辑只写一份；两条链路各自吞异常并返回 (answer, error)，单链路故障不导致 5xx。

已落地
Cache

四级缓存，实际用了哪一层

标准 RAG 流水线的四级缓存中，本项目只落地了第一层，且只覆盖 FAQ 链路。

Roadmap

后续可添加 / 可修改

以下均为代码中已存在的改动入口，每条都标注了当前状态与可改动的位置。

01

FAQ 命中阈值

固定 0.85 与语料规模耦合；可改 min-max 或 top1-top2 间隔，阈值移入配置。

02

MySQL 连接

单连接 + 锁，无重连；可加 ping(reconnect=True) 或连接池。

03

LLM 客户端封装

两处封装参数不一致；可抽公共 llm_client，统一 temperature / 超时 / 重试。

04

调试输出与旧分派

print、两处 pass、旧 if/elif 分派均已注释停用；确认后可删除。

05

学科配置与语料

valid_sources 含 ops 但无语料；可补 ops_data/ 或从配置移除。

06

密钥管理

config.ini 明文存 API Key；可改为环境变量注入。

07

观测字段

当前只返回 engine / elapsed / note；可补 cached、分段耗时与 trace id。

08

子查询结果清洗

直接 split('\n') 未过滤空行与编号，is None 判断恒假；可清洗后再检索。

Get started

terminal 
pip install -r requirements.txt

# Flask 同步版
python app.py            # → http://127.0.0.1:5000

# FastAPI 异步版
python app_async.py      # → http://127.0.0.1:8000

}
